This client-side JavaScript library allows you to embed a visual form on your own website
to fill out PDF templates and generate PDFs.

<LinkCard
  title="Embedded Visual Forms Guide"
  href="/docs/guides/embedded-forms/embedded-visual-forms/"
  description="Learn how to embed our visual forms on your website"
/>

<Aside type="caution">
  The visual forms library does not provide any ESIGN/UETA compliance features
  such as audit trail logging. Signature Requests JS uses it inside a secure
  iframe to show the signing form for a [signature
  request](/docs/guides/embedded-forms/embedded-signature-requests/). Use
  signature requests if you need to collect legally binding signatures.
</Aside>

You can also [get these release notes by email](https://app.docspring.com/email/subscribe?list=visual_form).

## Changelog

### 2.19.1 <span class="ml-2.5 relative -top-0.5"><Badge text="Latest" variant="success" size="small"></Badge></span>

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 30, 2026
</div>

- The request that creates a submission sends the page's CSRF token, like the
  requests that wait for its PDF. DocSpring's API now checks the token when a
  browser that's signed in to DocSpring calls it.

### 2.19.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 29, 2026
</div>

- Logs a deprecation warning in the browser console when the page passes the
  `apiTokenId` and `apiTokenSecret` options. They put an API token in the
  page, where anyone can read it and use your account. They still work: remove
  them, replace the token, and get private submissions' PDFs on your server
  ([Private Submissions and API
  Tokens](/docs/forms/visual-forms/#private-submissions-and-api-tokens)).
- Works on a page whose Content-Security-Policy doesn't allow inline styles
  (no `'unsafe-inline'` in `style-src`). The tooltips' CSS is now in the
  form's stylesheet, and the dropdowns and the signature font picker no longer
  add `<style>` elements. See
  [Content Security Policy](/docs/forms/js-libraries/content-security-policy/).
- A form with a signature field now loads in a container without the
  `dsp-form` class, whatever selector you pass to `createVisualForm`. Earlier
  versions stopped with "No elements were found for selector .dsp-form".

### 2.18.2

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 27, 2026
</div>

- Text is a little darker, for better contrast, and borders are a slightly
  different grey. Buttons and field highlights keep their colors.
- New icons for closing the signature window and resetting a field.
- An inline signature pad shows a signature that is already in the form's data
  (from a saved draft, for example), instead of an empty pad.

### 2.18.1

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 27, 2026
</div>

- [Conditional logic](/docs/template-editor/conditional-logic/) now runs on the
  same rule engine as web forms and PDF generation, so a rule shows, hides and
  requires the same fields everywhere.
- A rule that targets a group or a list by its name (which the API allows) now
  shows and hides every field in it, and a group or list that a rule requires
  needs a value in at least one of its fields. Earlier versions ignored these
  rules.
- A rule that also targets a field inside a list's rows, which isn't supported
  yet, now still shows and hides its other fields, as the PDF does.
- A group whose fields are all numbered (`phones/0`, `phones/1`) is a list, as
  in the API's schema: a rule can target the list, but not the fields in it.
- Number conditions read only decimal numbers, such as `5`, `-1.5` or `1e3`, as
  numbers: a field's value `0x10` isn't 16. A Greater or Less rule with a bound
  like `0x10` is ignored, In Range treats it as an open bound, and Equals
  compares it as text.

### 2.18.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 26, 2026
</div>

- A template with a static _Number_ field that has a default or a formula can
  be submitted. The form sent the field's value, which the template's JSON
  schema doesn't allow, so the submission failed. The value is still shown, and
  calculated again when the PDF is generated.
- The form ignores values for a field that is static in the template, in
  `defaultFormData`, `staticFormData` or a field override of a static _Number_
  field's default, and shows the template's value, which the PDF prints. The
  API rejected a submission with them. A template that allows additional
  properties accepts them, so the form keeps and submits them, as before. The
  `onSubmit` callback still gets every static field's value.
- Image fields with a default value no longer make the submission fail. The
  default isn't sent: the PDF shows it when the field is optional and left
  empty.
- Check marks and shapes match their _Condition_ as the PDF does. _Starts
  With_, _Ends With_ and _Regex_ conditions no longer stop the form from
  loading, and _Number_ conditions are applied. A _Regex_ is matched as Ruby
  matches it, apart from some [Ruby-only
  syntax](/docs/reference/field-data-types/#conditions) that the form doesn't
  support. A _String_ check mark or shape whose _Equals_ condition is empty is
  selected only when its value is empty, as the PDF draws it. It was always
  shown selected.
- Clicking a selected optional check mark or shape clears it, also when a longer
  value selects it (_Starts With_, _Ends With_ or _Contains_). A _Regex_ check
  mark only shows whether the value matches: clicking it doesn't change the
  value.
- Images passed in `defaultFormData` or `staticFormData`, or sent with the
  submission, count as filled in and are shown. So do signatures and initials
  on a visual form. One the form can't preview (a URL or an uploaded image ID)
  shows "Image added", "Signed" or "Initialed". A typed signature with a blank
  name doesn't count as signed.
- A prefilled image that the field only shows can't be replaced: clicking it no
  longer opens the file picker.
- In a signature request, only the signer can sign: the form ignores
  signatures and initials in `defaultFormData` and `staticFormData`, and a
  signature field the request asks for starts empty. A signature the submission
  already has for another field is shown read-only, and no longer stops the
  signer from finishing.
- A field whose options were removed in the template editor shows a text input
  instead of an empty drop-down.
- A static field with options, or a field whose value is shown read-only, shows
  its value instead of a drop-down. A required drop-down can be changed but no
  longer cleared.
- An option list with spaces after its commas (`Yes, No`) no longer rejects the
  options after the first one.
- Fields for each item of a list (named like `items/0/code`) are checked item by
  item. A required one no longer stops the form from being submitted when every
  item is filled in, and max length, number limits, email and option checks
  apply to each item. An empty item before a filled one is sent as an empty
  item instead of `null`, which the API rejected. In a signature request, a
  field list that names a list's field with `~` (`items/~/code`) asks for every
  item, and one that names an item (`items/0/code`) asks for only that item.
- A _Number_ field named `length` is submitted with the form.
- Shows the dates in fields named `@@signature_requests/N/completed_at` and
  `viewed_at`, the new name for `@@data_requests/N/...` (which still works).
- A `completed_at` or `viewed_at` field for another signer shows the dates of
  the signature request with index N, as the PDF does (see
  [special field names](/docs/template-editor/field-names/#special-field-names-for-signature-requests)).
  When no signature request had that index, it showed the next signer's dates.
- The internal error for a form opened without its signature request options
  names the missing options, without their values.
- `onError` gets `{ error, message }` when the PDF couldn't be generated
  (`processing_failed`), and once when it takes more than a minute
  (`processing_timeout`) while the form keeps waiting. It got nothing before,
  every second after the first minute. A failed save still passes the request's
  error.
- Waiting for the PDF carries on after a failed status check, and stops after
  five in a row. It stopped at the first.

Signing forms (signature requests):

- A signer can only fill in the fields the signature request asks them to fill in.
  Every other field is read-only and shows what the PDF will print, and isn't
  shown when there's nothing to print. DocSpring only saves the signer's own
  fields.
- `setField()`, `defaultFormData` and `staticFormData` only fill in the
  signer's own fields. `setField()` can't fill in a signature or initials field:
  only the signer signs.
- `submitForm()` shows the **I Agree** step, as the **Continue** button does
  (or the fields that still need a value). The signer agrees to submit.
- Opened by Signature Requests JS 3.0.0, the form ignores `setField()`,
  `submitForm()`, `defaultFormData`, `staticFormData` and `domainVerification`,
  and sends `onError` an `error` code and a `message` for every error.
- The form only takes messages from the page that opened it, takes the page's
  options once, and only the options Signature Requests JS (or Data Requests
  JS) sends.
- A read-only image or signature field no longer opens the file picker or the
  inline signature pad.
- A list field or multiline field that the signature request asks for is shown even
  when it's empty, and static and combined fields are shown.
- An image or signature that the PDF prints from a URL shows the copy that
  DocSpring downloaded when the submission was created, which the PDF prints,
  and **Loading image…** until it's downloaded.

In visual forms and signing forms:

- A combined field shows what the PDF prints, including other signers' values,
  with each value formatted as the PDF prints it (dates in their date format,
  numbers with their decimal places, check boxes as their true or false text).

### 2.16.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 20, 2026
</div>

- Added the `allowSkippingOptionalFields` option and support for the template's
  [Show Continue Once Required Fields Are Filled
  In](/docs/forms/visual-forms/#show-continue-once-required-fields-are-filled-in)
  setting, so the **Continue** button can appear as soon as every required field
  is filled in. Values passed in `defaultFormData` now count as filled in.
- Required fields are highlighted in the template's [required field
  color](/docs/forms/visual-forms/#required-field-color), when it has one.
- A field's background color is shown at the field's opacity, as in the PDF.
  Translucent static shapes are no longer drawn fainter than in the PDF.
- Text fields stop accepting characters at the field's maximum length. A value
  that is already too long (for example from `defaultFormData`) shows an error
  on the field instead of failing when the form is submitted.
- Unchecking an optional radio button, or clearing an optional number, select
  or date field, no longer makes the submission fail. `onFieldChange` gets the
  value that is stored: `null`, or on accounts that use template JSON schema
  version 1, `''` or `undefined` (the value is left out), depending on the
  field's type. On schema version 1, a default or prefilled value then comes
  back (see [Clearing Optional
  Fields](/docs/forms/visual-forms/#clearing-optional-fields)).
- A field keeps showing its default value, `defaultFormData` value or formula
  result while the user is in it, instead of going blank, and the user edits it
  like any input. Moving to a field with **Tab**, **Shift+Tab** or the **Next**
  button selects its text, so typing replaces it.
- A cleared optional text, email or URL field stays empty, instead of its
  default value coming back. A cleared required field still gets its default
  back when the user leaves it.
- A text, number, email or URL field the user has changed shows a ↺ button,
  which puts back what the field showed before: its default value, its
  `defaultFormData` value, its value from the submission, or what its formula
  calculates now. `onFieldChange` gets `undefined` (the user's value is
  removed), or the submission's value in a data request.
- **Shift+Tab** moves to the previous field, the arrow keys move between the
  options of a radio button group, and **Space** selects a radio button like a
  click. An inline form only takes these keys while the user is in it, so it no
  longer takes the Tab key from the rest of your page. See
  [Keyboard](/docs/forms/visual-forms/#keyboard).
- When DocSpring rejects the submitted data, the form names each field and says
  what is wrong with it, instead of asking the user to refresh the page. Number
  fields' minimum and maximum values are checked before the form is submitted.

### 2.15.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 18, 2026
</div>

- New global functions: `DocSpring.getFormData()` returns the values entered in
  the form, and `DocSpring.setFormData(data)` replaces them. Fields that `data`
  leaves out go back to their default values. Static fields, and fields set with
  `staticFormData`, keep their values.
- New `metadata` option: an object that is saved with the submission.
- The `test` option can be a function, called when the form is submitted.
- A form inside a hidden element no longer handles key presses or measures its
  fields. After you show it, send a window `resize` event so it measures them.
- The Tab key moves to the form's next field only while the focus is in the form
  (or nowhere on the page), so it can still reach the rest of the page.

### 2.11.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 18, 2026
</div>

- Date fields show the date the PDF will print. Dates sent as NN/NN/YYYY are
  read day first, or in the order of the template's date format when the
  template's **Parse Dates Using the Template's Date Format** setting is on.
  Before, the form read them month first and could show a different date from
  the PDF.
- The date picker shows dates in the template's default date format when the
  field has no format of its own, as the PDF does.
- Dates sent as YYYY-MM-DD no longer show as the day before in time zones
  behind UTC.
- Static date fields show their default value as written, as the PDF prints
  it. Before, the form reformatted it as a date.

### 2.9.0

<div class="mt-2.5 text-sm text-gray-500 dark:text-gray-400">
  Released on Oct 13, 2026
</div>

- [Formulas](/docs/template-editor/formulas/) are calculated the same way as
  in the generated PDF, so the form shows the values that will be printed.
- A formula stays blank until one of the fields it uses has a value. Default
  values don't count.
- If a formula can't be calculated with the values entered (for example, when
  it divides by zero), the form shows the problem on the field and can't be
  submitted until the values change. A problem with a formula that the form
  doesn't ask for is shown at the top of the form.
- In a data request with more than one signer, formulas are calculated with
  every signer's values.
- Formulas can use fields in a list of objects, and a field in a list can have
  a formula that is calculated for each row.
- Number fields show the values passed in `defaultFormData` or already saved on
  the submission, instead of their default value or formula.
