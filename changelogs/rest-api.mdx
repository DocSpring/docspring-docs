## Changelog

### API v2

- [API v2](/docs/api-guide/migrating-to-api-v2/) is the current version of the
  API, and the 4.x API clients call it. API v1 and the 3.x clients keep
  working.
- API v2 calls data requests signature requests. New data requests get IDs
  that start with `srq_` instead of `drq_`, in both API versions. Existing ones
  keep their IDs.
- Signing links expire, in both API versions. A signature request token's link
  (`api`, the default) opens the signing form for 24 hours, and an `email`
  token's for 7 days. A signing page that opened in time keeps working for 7
  more days, so the signer can finish later. Before, links never expired,
  whatever API v1's `expires_at` said. Tokens created before this change get
  the same lifetimes, counted from when they were created: an older link no
  longer opens the form, but a page the signer opened in the last 7 days still
  works.
- Live signature requests (data requests in API v1) work on every plan,
  including the free Developer plan. Creating one no longer returns
  `403 Forbidden` with `"code": "upgrade_required"`.
- A webhook with **Include submission data** turned off no longer sends any
  form values: each data request's (signature request's) `data`, `ip_address`
  and `user_agent`, and the submission's `truncated_text`, are `null`.
- The events of a test submission created with a live API token go to "Test
  only" webhooks, not "Live only" ones.
- API v1 changes for signature requests (data requests):
  - A signature or initials value in the data of a submission with data
    requests makes it an `invalid_data` submission: only the signer signs. A
    signed PDF is always static, whatever `editable` says.
  - On a public template, only the template's own account can send
    `data_requests`, `html`, `css`, `password`, `expires_in` or `editable`:
    other callers get a `422`. Their `field_overrides` only keep `hidden`,
    `backgroundColor` and `required`.
  - The data request events API only takes `send_request` events, and a
    completed, declined or expired data request takes no more updates, tokens
    or events (`422`).
  - A test API token gets a `403` when it creates a token or an event for a
    live data request, or updates one.
  - A submission with data requests can't be reprocessed, and a published
    template version's PDF can't be replaced.
- Other API v1 fixes:
  - `POST /templates` with `html` and no `template_type` creates an HTML
    template.
  - `POST /custom_files` without a `cache_id`, and downloading a combined
    submission that has no PDF, are `422`s.
  - EAN-13, EAN-8 and UPC-A barcode fields take the code with its check digit,
    and a wrong check digit is a data error when you create the submission.

### October 2026

These changes apply to accounts on the current plans (Developer, Starter,
Growth and Scale), except the `account_suspended` change, which applies to
every account. Accounts on a plan purchased before prepaid credits keep their
existing pricing and API rate limits.

- Submissions and combined submissions have a new state,
  `insufficient_credits`: a live PDF your credit balance can't cover is saved
  and resumes automatically when you add credits. Work that is still waiting
  after 30 days, or that you discard, moves to `error`, and DocSpring sends the
  `submission.failed` or `combined_submission.failed` webhook. No webhook is
  sent when work starts waiting.
- Creating a submission, batch or combined submission that your balance can't
  cover returns `402 Payment Required` with `"code": "insufficient_credits"`
  and the saved submission in the body. Synchronous requests return `402` too.
- Requests that need a higher plan (adding templates over your plan's limit,
  live data requests, the embedded template editor) return `403 Forbidden` with
  `"code": "upgrade_required"`. Nothing is saved.
- Creating submissions, batches or combined PDFs on a suspended account returns
  `403 Forbidden` with `"code": "account_suspended"`. Nothing is saved.
- Submissions and combined submissions that were already saved when an account
  was suspended wait in the `account_suspended` state instead of moving to
  `error`, and are generated when the account is reactivated. As with
  `insufficient_credits`, work still waiting after 30 days, or that you
  discard, moves to `error`.
- API requests are limited per account by plan, with separate limits for live
  and test API tokens. Responses include `RateLimit-Limit`,
  `RateLimit-Remaining` and `RateLimit-Reset`, and requests over the limit get
  `429 Too Many Requests` with `Retry-After`.
- If you use a DocSpring [API client](/docs/api-guide/install-api-client/),
  upgrade it to the latest version. Older versions of the Ruby, Python, PHP,
  Java and C# clients raise an error when they read the `insufficient_credits`
  state.

These expiry changes apply to every account:

- Expiring a submission also clears its metadata, schema errors, overflow text,
  PDF password, error message, rendered HTML, and the submitter's IP address,
  browser and location. An expired submission returns `metadata` and
  `truncated_text` as `{}`, `json_schema_errors` as `[]`, and `password` and
  `error_message` as `null`. A request that was waiting for credits keeps its
  "Not processed" error message. The `submission.expired` webhook has the
  cleared values too, so match it to your records by its `id`.
- Expiring a combined submission also clears its metadata, password and error
  message, and removes the URLs from `source_pdfs`.
- The `actions` of an expired submission or combined submission keep their
  state, with `result_data` as `{}` and `error_message` as `null`.
- A submission that doesn't process (any state other than `processed`, such as
  `error` or `invalid_data`) is kept for at least 48 hours before it expires,
  even when `expires_in` or the template's expiry is shorter, so you can debug
  it and a retry still has its data. Its `expires_at` shows when. A processed
  submission keeps your expiry setting, and a failed submission that is later
  processed expires that long after processing.
- Submissions saved with invalid data now expire like any other. Before, they
  were never deleted.
- A combined submission with `expires_in` that fails now expires too, after at
  least 48 hours. Before, failed combined submissions were never deleted.

This processing change applies to every account:

- A submission or combined submission that hits an unexpected error on our
  side is retried for about a minute while it stays `pending`, then moves to
  `error` and stays there, with a message saying what happened. Before, it
  moved to `error` and could still be retried and reach `processed` hours or
  days later.
