Click **Settings** in the template editor's top bar to change a template's settings. They're in tabs: **General**,
**PDF output**, **Forms**, **Submissions**, **Embedding**, **Webhooks**, **Emails**, **Field defaults** and **Advanced**. Each
setting below says which tab it's on.

The **Field defaults** tab sets the typeface, colors, date formats and other options that fields use when they don't
set their own. In an HTML or Word template, they're how its form fields print the values that signers fill in
([HTML](/docs/html-templates/overview/#form-fields), [Word](/docs/word-templates/tags/#form-fields)), apart from the
text's size and the text's and checks' color, which follow the text around each form field's tag. A page design's
form fields set their own size, color and alignment, and print in Helvetica, so its tab has only the date formats and
the color that marks the fields a signer must fill in.

## Locked

_On the General tab._ Locked templates cannot be changed or deleted. See [Locked Templates](/docs/template-editor/locked-templates/).

## Expire Submissions

_On the Submissions tab._ A template's submissions follow [your account's expiry settings](#the-accounts-expiry-settings) unless **Override the account's expiry settings** is on. With it on, the template sets its own for all its submissions, shorter or longer than the account's:

- If _Expire submissions_ is **off**, we store the template's submission data and the files they make (PDFs, Word documents and OpenDocument files) until you delete them, whatever the account's settings.
- If _Expire submissions_ is **on**, we delete each submission's data and metadata, the PDF, Word document or OpenDocument file it made, any uploaded images, and the submitter's IP address, browser and location after the time set beside it (_5 minutes_, _24 hours_, _7 days_, etc.)

A template with signature or initials fields gets its submissions from signature requests, so for it, _Expire submissions_ also deletes their signed PDFs, audit trails and the records of who signed and when. We keep a record of each signing's hashes for at least 10 years, so a copy can still be verified: see [Signing evidence and retention](/docs/forms/signing-evidence/). The editor warns you about it while it's on.

Expiry counts from when each submission is processed. A request's `expires_in` overrides both the template's and the account's settings.

A submission that fails (for example, with invalid data) is kept for at least 48 hours before it expires, even if the expiration time is shorter, so that you can see what went wrong and a retry still has its data.

Test submissions are deleted after 30 days at the latest.

You can also [make an API request](/docs/api/#tag/submissions/delete/submissions/{submission_id}) to immediately expire a submission.

### The account's expiry settings

_On the Account page's Data retention tab._ Three settings decide how long the account keeps what it stores. Each has its own card and **Save** button:

- **Submissions**: submissions without signature requests, from templates that don't override the account (through the API or your forms) and from form library fills. New accounts start at 30 days.
- **Signed documents**: submissions with signature requests, from templates that don't override the account. New accounts keep them until you delete them.
- **PDF tools**: the PDFs you combine with the API, unless the request sets `expires_in`. New accounts start at 1 day.

Accounts created before these settings were added have all three off, so they keep their live submissions until they're deleted. Test submissions are deleted after 30 days on every account. The exception is an account whose **Template defaults** expired new templates' submissions: its **Submissions** and **Signed documents** settings have that length, so its new templates still expire as they did.

The tab also says how many templates set their own expiry. New templates follow these settings. A template sets its own only when you turn on **Override the account's expiry settings** in its settings, or an API request turns on `expire_submissions`, creates the template with `expire_submissions` set (on or off) or sets `override_account_expiry`: **Template defaults** has no expiry settings.

### Changing an expiry setting

Changing one of the account's expiry settings, or a template's, applies to the submissions and combined PDFs you already store, not only to new ones:

- **Turning expiry on, or shortening it**, deletes what's already older than the new setting. About a minute after the change, we email the account's owner and whoever made the change, with how many are that old and when they'll be deleted: 24 hours after the email, oldest first. To keep them, change the setting back before then. If nothing is that old yet, there's no email, and the new setting applies as each one reaches that age.
- Each save sends one email, even when it changes the expiry of a template's submissions both with and without signature requests.
- On the Account page, saving a change that deletes older data asks first, with the count. The template editor saves as you go, so it shows a notice with the date instead.
- **Turning expiry off, or lengthening it**, applies at once: what you store is kept for the new length, or until you delete it.
- Submissions and combined PDFs created with their own `expires_in`, and ones still waiting for signatures or credits, keep their own expiry.

## Allow Additional Properties

_On the Submissions tab._ By default, the data that you submit must exactly match the JSON schema. Any additional properties will cause a validation error. This guarantees that you haven't forgotten to add any fields to your template, and it also guards against accidental field deletion.

When the **Allow additional properties in JSON data** setting is enabled, additional properties in your data will be silently ignored. This can be useful when you don't have full control over the JSON data (e.g. a webhook integration with a third-party service.) A misspelled field name is ignored too: its field is left blank, or the submission fails if that field is required.

## Encrypt PDFs with a Password

_On the PDF output tab._ When **Encrypt PDFs with a password** is checked, generated PDFs are encrypted with the
**PDF password**, and can only be opened by entering that password. (This is called a "user password".)

## Merge Audit Trail With Signature Request PDFs

_On the PDF output tab._ When checked, audit trail pages are appended to the generated PDF when a submission has signature requests. When unchecked, the audit trail PDF can be downloaded separately.

## Add Submission ID Footers to Signature Requests

_On the PDF output tab._ When checked, the submission ID is added to the bottom right corner of each page when a submission has signature requests.

## Parse Dates Using the Template's Date Format

_On the Field defaults tab, for PDF templates only._ This setting is under the default date formats (**Parse dates
using format**).

We recommend sending date values as `YYYY-MM-DD` (see [Date](/docs/reference/field-data-types/#date)). Dates sent as numbers like `05/07/2024` (with slashes, dashes or dots) are read day first by default, so `05/07/2024` is July 5, and a date like `05/13/2024` can't be read and is left blank.

When **Parse dates using format** is checked, these dates are read in the same order as the template's default **Date** format: month first for `%m/%d/%Y`, and day first for `%d/%m/%Y`. Fields that include a time use the default **Date/time** format. Dates sent as `YYYY-MM-DD` are read the same way either way.

Each template version keeps its own setting. If your template has published versions, publish a new version after changing it: API submissions use the latest published version by default (see [Template Versions](/docs/template-editor/versions/)).

You can also set this for new templates on your account's **Template defaults** page, and change it with the `parse_dates_using_template_date_format` option in the [templates API](/docs/api/#tag/templates).

## HTML Page Settings

_On the PDF output tab._ HTML templates have **Page format**, **Landscape**, **Width**, **Height**, margin and
**Print background** settings. See [Page Settings](/docs/html-templates/overview/#page-settings).

## Online Form Privacy

_On the Forms tab._ Set this to **Public** to allow anyone to fill out the online form if they have the URL.

## Online Form

_On the Forms tab, as **Form type**._ Which form a PDF template's online form link opens: the **web form** (questions on a page), the **visual form** (fields
filled in on the PDF), or **both**, in two tabs. A `mode` parameter in the link overrides it (see
[Web Form, Visual Form or Both](/docs/forms/web-forms/#web-form-visual-form-or-both)). HTML templates don't have this
setting: they have no visual form, so they always show the web form.

You can also set this on your account's **Template defaults** page, for new templates and, with **Update Templates**,
for existing ones. HTML templates stay on the web form either way.

## Fill Out Sections in Order

_On the Forms tab._ For a web form with [sections](/docs/forms/web-forms/#sections). When this is on, people move on
with **Next**, and a later section stays locked until they reach it. When it's off, which is the default, they can open
any section from the list beside the form, and **Next** and the submit button still check their answers.

You can also set this on your account's **Template defaults** page, for new templates and, with **Update Templates**,
for existing ones.

## After Submitting

_On the Forms tab._ What the [web form](/docs/forms/web-forms/#after-the-form-is-submitted) shows once someone submits
it:

- **Title after submitting**: the success screen's title. Leave it empty to show "Thanks for filling out" and the
  template's name.
- **Message after submitting**: shown under the title, as plain text. Line breaks show, and web addresses become links.
  One short paragraph (up to 90 characters) is centred under the title, and a longer message is shown in a shaded box,
  aligned left.

The title and the message can have [variables](/docs/forms/web-forms/#variables) such as `{{ data.first_name }}`,
which show the person's answers.

- **Show a Fill out again button**: the button clears the form, so someone can fill it in again. On by default.

The web form doesn't show its success screen when it redirects to a [Redirect URL](#redirect-url).
[Web Forms JS](/docs/forms/js-libraries/web-forms-js/#success-screen) options can override these settings. You can also
set them on your account's **Template defaults** page.

## Show Continue Once Required Fields Are Filled In

_On the Forms tab. On by default._ Visual forms and signature requests have a **Next** button
that takes the user through each field in turn. With this setting on, a **Continue** button appears next to it as soon
as every required field is filled in, so users can skip the optional fields, and **I Agree** lists the ones they
skipped. Turn it off to show **Continue** in place of **Next** only once every field has a value or has been visited.
In the API it's the template's `continue_before_optional_fields`. The `allowSkippingOptionalFields` option of
[Visual Forms JS](/docs/forms/js-libraries/visual-forms-js/) and
[Signature Requests JS](/docs/forms/js-libraries/signature-requests-js/) overrides this setting either way.

## Submission Privacy

_On the Submissions tab._ Set this to **Public** to allow anyone to view submission data and download their PDF if they have the URL.

This is useful when you have added a [@@data_url QR code to the PDF](/docs/template-editor/field-names/#special-field-names).
(`@@data_url` is a URL where the submission data can be viewed or downloaded.)

## Webhook URL

Configure webhooks on the [Webhooks page](https://app.docspring.com/webhooks). See [Webhooks Overview](/docs/webhooks/overview/).

Existing legacy webhook URLs on templates and API tokens (shown on the **Webhooks** tab as **Legacy webhook URL**) keep working until they are migrated to the new webhooks system.

## Slack Webhook URL

_On the Webhooks tab._ Posts a message to a Slack channel whenever this template generates a PDF. Each message links to the PDF and to its
submission. Test PDFs and combined PDFs don't post a message.

To get a URL, create a Slack app with an incoming webhook for the channel
([Slack's guide](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks)), then paste the webhook URL
into this field. Messages show your Slack app's name and icon.

On the free Developer plan, each Slack webhook URL is one of the account's 2
[active integrations](/docs/billing/#plans). Using the same URL on more
templates doesn't count again.

## Email Actions

_On the Emails tab._ Email each submission's PDF to the people who filled it in, or to your team, with your own subject
and message. See [Email Actions](/docs/template-editor/email-actions/).

## Signature Request Emails

_On the Emails tab._ How DocSpring emails the people who sign this template's
[signature requests](/docs/api-guide/create-signature-requests/#emails-from-docspring). A request's own `reply_to` and
`notification_emails` replace the template's. You can set them for new templates on your account's **Template
defaults** page, and with the `signature_request_*` options in the [templates API](/docs/api/#tag/templates).

- **Sender name**: Who your signers see the emails are from, as in "Acme via DocSpring". Leave it empty to use your
  account's name.
- **From address**: _Growth and Scale plans._ An address at one of your verified email domains, the same domains as
  [email actions](/docs/template-editor/email-actions/). Leave it empty to send from DocSpring's shared address, with
  "via DocSpring" after the sender name. While the address can't be used (its domain is no longer verified, or your
  plan no longer includes it), new signature requests that DocSpring emails are refused until you change it. Emails
  for requests created before that go from the shared address, and your account owner gets an email.
- **Signing URL**: _Growth and Scale plans._ A page on your own site that the email's button opens instead of
  DocSpring's signing page: an `https` URL on one of your verified email domains or a subdomain of one. It must include
  `{{ signature_request_id }}`. Your page checks who the signer is, then
  [creates a token](/docs/api/#tag/signature-requests/post/signature_requests/{signature_request_id}/tokens) and opens
  the [signing form](/docs/guides/embedded-forms/embedded-signature-requests/). The audit trail still says the signer
  was authenticated by an email link (`email_link`): DocSpring emailed the link to their address, whichever page it
  opens. While the URL can't be used (its domain is no longer verified, or your plan no longer includes it), new
  signature requests that DocSpring emails are refused until you change it, and emails with a link for earlier
  requests aren't sent. Your notification emails get an email about it.
- **Include the signing token**: Adds a signing token to the signing URL, as `{{ token_id }}` and `{{ token_secret }}`,
  so your page can open the signing form without creating a token. Anyone who has the email can then sign, as with
  DocSpring's own link.
- **Reply-to address**: Where your signers' replies go: a team member's address, or one at your verified email
  domains. Leave it empty to use your account owner's.
- **Notification emails**: Who DocSpring emails when a document is completed or declined, or an email to a signer
  bounces or can't be sent. Up to 10 team members or addresses at your verified email domains. Leave it empty to email
  your account owner.
- **Signed PDF**: How the emails that send signers and CCs the signed PDF include it: attached (a download link when
  it's too big to attach), or a download link. The default is a link if your account has signed a BAA, otherwise
  attached. An [email action](/docs/template-editor/email-actions/) that sends the PDF to one of these people replaces
  DocSpring's email to them.

## Redirect URL

_On the Forms tab, under After Submitting._ We'll redirect users to this URL whenever they fill out the online form to
generate a PDF, instead of showing the web form's success screen.
This applies to online forms hosted on [docspring.com](https://docspring.com),
and [embedded forms on your own website](/docs/guides/embedded-forms/embedded-web-forms/).
The submission ID, template ID, and template name will be appended to the URL as query params.

After its `?` or `#`, the URL can have [variables](/docs/forms/web-forms/#variables) such as
`?name={{ data.first_name }}`. Web forms, visual forms and signature request pages fill them in with what the person
submitted.

## Template Description

_On the General tab._ The template description is shown under the template's name at the top of its [online form](/docs/forms/web-forms/), in
every mode, and is the page's meta description. It is not shown on embedded forms or signature requests.

## Embedded Template Editor Settings

These are on the **Embedding** tab.

- **Embed domains**: Not shown in the embedded editor. A comma-separated list of domains where you embed the template editor, visual forms or signature request forms. The template editor accepts wildcards such as `*.example.com` and isn't restricted when the list is blank (see [Embed Domains](/docs/guides/embedded-template-editor/#embed-domains)). [Embedded visual forms](/docs/guides/embedded-forms/embedded-visual-forms/#embed-domains) only load on the listed sites, accept the same wildcards and ports, and aren't restricted when the list is blank. Live [embedded signature requests](/docs/guides/embedded-forms/embedded-signature-requests/) only load on the listed sites, accept the same wildcards and ports, and don't load on any site when the list is blank; test signature requests load anywhere. A path (`example.com/forms`) is dropped when you save.
- **Embed edit token**: Not shown in the embedded editor. The token you use with `template_editor.js` to embed this template editor. You can show or regenerate it. See [Embed Edit Token](/docs/guides/embedded-template-editor/#embed-edit-token).
- **Embedded editor permissions**: Not shown in the embedded editor. Allow embedded editor users to change template settings, to publish, restore, and delete versions, or to replace the PDF document. By default they can only edit fields and layout. See [Security](/docs/guides/embedded-template-editor/#security).
- **Predefined fields**: _PDF templates only._ The field names that embedded editor users can add. See [Use Predefined Fields](/docs/guides/embedded-template-editor/use-predefined-fields/).

## Template PDF

_On the General tab, for PDF templates only._ Shows the template's PDF file. Drop a new PDF onto the upload area to replace it. The template
keeps its fields.

To replace the fields too, check **Re-import fields from the new PDF** before you drop the new PDF. When the PDF has
been processed, all of the template's fields are replaced with the fillable fields in the new PDF, the same way as when
you first uploaded a PDF (the fields can't be edited until then). Fields you added or changed in DocSpring are removed.
The default typeface, font size, bold and color are taken from the new PDF's fields, and the template's other settings
are kept. Click **Undo** in the message that appears to put the previous fields and defaults back. If the new PDF has no
fillable fields, the template keeps its fields.

With the API, send the new PDF with `reimport_fields` set to `true`:
[`PUT /templates/{template_id}/document`](/docs/api/#tag/templates/put/templates/{template_id}/document) takes a
`document_url`, `document_base64` or an uploaded `cache_id`, and
[`PUT /templates/{template_id}/document/upload`](/docs/api/#tag/templates/put/templates/{template_id}/document/upload)
takes a multipart upload. In our API clients, these are `updateTemplateDocument` and `uploadTemplateDocument`. A
re-import isn't allowed on a locked template.
